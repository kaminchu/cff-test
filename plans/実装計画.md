# cff-test 実装計画

## 1. この文書の目的

`plans/要件.md` に記載された構想を、別の AI エージェントが追加の設計判断をせずに実装できる粒度へ具体化する。

実装対象は、CloudFront Functions の JavaScript コードをローカルで静的検査・実行・JSON 比較できる Rust 製 CLI `cff-test` である。成果物は QuickJS を内包した単一の実行ファイルとし、Node.js、AWS CLI、AWS 認証情報、外部 JavaScript ファイルには実行時依存しない。

## 2. 要件の解釈と固定する前提

要件書だけでは複数の解釈が可能な箇所を、実装者ごとの差が出ないよう次のとおり固定する。

1. 対象は CloudFront Functions JavaScript runtime 2.0 の viewer request / viewer response 関数とする。runtime 1.0 と Connection Functions は対象外とする。
2. イベントオブジェクトの対象バージョンは `1.0` とする。
3. JavaScript のエントリーポイントは、ソースのトップレベルに宣言された `handler(event)` または `async handler(event)` とする。Node.js Lambda 形式の `exports.handler` は対象外とする。
4. `check`、`run`、`test` を正式なサブコマンドとする。サブコマンド省略形は要件書の例どおり `test` と同じ意味にする。
5. `run` と `test` は必ず静的検査を先に実施し、エラーが1件でもあれば JavaScript を実行しない。
6. `Date` の「現在時刻」は1回のハンドラ呼び出し中だけ固定する。通常はコマンド開始時刻、`--now-ms` 指定時はその Unix epoch milliseconds を使う。
7. CloudFront KeyValueStore は AWS に接続せず、`--kvs` で与えたローカル fixture から `cloudfront` モジュールの `kvs()/get()/exists()/meta()` を再現する。
8. runtime 2.0 に追加された `cloudfront.cwt` は要件に明記されていないため初期版の対象外とする。静的検査では未対応機能としてエラーにする。
9. `ComputeUtilization`、AWS 内部エンジンの不具合・癖、AWS と完全に同じエラー文、非公開挙動は要件書どおり対象外とする。
10. AWS の実環境と同一の性能・メモリ消費を保証しない。無限ループや異常割り当てから CLI を守るローカル安全制限は設けるが、CloudFront の compute utilization の再現とは呼ばない。

実装時は以下を一次資料とし、ブログや Node.js の一般仕様を CloudFront 固有仕様より優先しない。

- [Restrictions on CloudFront Functions](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-function-restrictions.html)
- [Quotas on CloudFront Functions](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-limits.html#limits-functions)

AWS 仕様は更新され得るため、実装開始時に上記ページの内容を再確認する。ただし、この計画の初期版スコープを勝手に拡張しない。仕様差分を見つけた場合は `docs/compatibility.md` の「既知の差異」に記録し、別変更として扱う。

## 4. 完成条件

次をすべて満たした時点を初期版の完成とする。

- `cff-test check function.js` が、runtime 2.0 の対応構文・グローバル・組み込み機能・禁止 API を位置情報付きで診断する。
- `cff-test run function.js -i event.json` が、制限された QuickJS 環境で `handler(event)` を1回実行し、戻り値を整形済み JSON として標準出力へ出す。
- `cff-test test function.js -i event.json -o expected.json` が実際値と期待値を JSON として比較し、差分の JSON Pointer と両方の値を表示する。
- `cff-test function.js -i event.json -o expected.json` が上記 `test` と同じ動作をする。
- `Date.now()`、`new Date()`、引数なしの `Date()` が同一実行中に固定時刻を返す。明示的な日時引数を持つ `new Date(value)` は通常どおり動く。
- `Buffer`、`crypto`、`querystring`、ローカル KVS を使う `cloudfront` モジュールが、本文で定義する範囲で動く。
- `eval`、`Function` コンストラクタ、タイマー、ファイルシステム、プロセス、環境変数、ネットワーク API が利用できない。
- viewer request / viewer response の入力と戻り値を検証し、ヘッダー名など CloudFront 固有の明確な制約違反を拒否する。
- 10 KB を超える関数コードを静的検査で拒否する。
- `cargo test`、`cargo clippy --all-targets --all-features -- -D warnings`、`cargo fmt --check`、`cargo build --release` が成功する。
- release バイナリを空の一時ディレクトリへコピーして、外部ランタイムなしで end-to-end テストが成功する。

## 5. CLI 仕様

### 5.1 コマンド形式

```text
cff-test check <FUNCTION>
cff-test run  <FUNCTION> -i <EVENT> [--kvs <KVS>] [--now-ms <MILLISECONDS>]
cff-test test <FUNCTION> -i <EVENT> -o <EXPECTED> [--kvs <KVS>] [--now-ms <MILLISECONDS>]
cff-test      <FUNCTION> -i <EVENT> -o <EXPECTED> [--kvs <KVS>] [--now-ms <MILLISECONDS>]
```

初期版では標準入力、複数イベント、設定ファイル、glob、watch mode、スナップショット更新を追加しない。入力は明示された UTF-8 ファイルだけを読む。

### 5.2 引数

| 引数 | 対象 | 必須 | 意味 |
|---|---|---:|---|
| `<FUNCTION>` | 全コマンド | yes | UTF-8 の CloudFront Functions JavaScript ファイル |
| `-i, --input <EVENT>` | run/test | yes | CloudFront event version 1.0 の JSON |
| `-o, --output <EXPECTED>` | test/省略形 | yes | `handler` の期待戻り値 JSON |
| `--kvs <KVS>` | run/test | no | ローカル KeyValueStore fixture JSON |
| `--now-ms <MILLISECONDS>` | run/test | no | 固定する現在時刻。符号付き64 bit整数の Unix epoch milliseconds |

同じオプションを環境変数から暗黙に読まない。CloudFront の環境変数非対応という制約と CLI の再現性を保つためである。

### 5.3 標準出力・標準エラー出力

- `check` 成功時: 標準出力へ `OK: <path> is compatible with cloudfront-js-2.0` を1行出す。
- `run` 成功時: 標準出力へ戻り値 JSON だけを2スペースインデント＋末尾改行で出す。
- `test` 成功時: 標準出力へ `PASS: <function>` を1行出す。
- JavaScript の `console.log()` は標準エラー出力へ1呼び出し1行で出す。JSON 出力と混在させない。
- 診断、比較差分、実行時エラーは標準エラー出力へ出す。
- 色は初期版では付けない。CI と端末で同じ出力にする。

### 5.4 終了コード

| code | 意味 |
|---:|---|
| 0 | 検査成功、実行成功、または比較一致 |
| 1 | 静的互換性エラー、イベント/戻り値検証エラー、JavaScript 実行エラー、JSON 不一致 |
| 2 | CLI 使用方法の誤り、ファイル I/O エラー、JSON 構文エラー、KVS fixture 構文エラー |

`clap` 自身の引数エラーも code 2 に揃える。panic は利用者入力に対して発生させない。

## 7. 技術選定

### 7.1 Rust と主要依存

- Rust stable、edition 2024。
- CLI: `clap` の derive API。
- JSON: `serde` と `serde_json`。
- エラー型: ライブラリ境界は `thiserror`、最上位の文脈付加は `anyhow`。エラー文字列だけで終了コードを判定せず、`AppError` の分類から決める。
- JavaScript AST: `swc_ecma_parser`、`swc_ecma_ast`、`swc_ecma_visit`。未束縛グローバル判定には SWC resolver の unresolved mark を使い、ローカル変数名を誤検知しない。
- JavaScript 実行: `rquickjs`。QuickJS/QuickJS-NG の C ソースを build dependency としてコンパイルし、実行時に共有ライブラリや `qjs` コマンドを要求しない構成にする。
- Buffer: AWS Labs LLRT の `llrt_buffer` を再利用する。CloudFront にない Node API は公開しないラッパーを置く。
- crypto: `md-5`、`sha1`、`sha2`、`hmac`、`base64` を用いた小さな Rust 実装にする。LLRT 全体や OpenSSL は導入しない。
- CLI 統合テスト: `assert_cmd` と `predicates`、一時ファイルは `tempfile`。

依存バージョンは互換性を確認した組み合わせを `Cargo.lock` に固定する。特に `llrt_buffer` と `rquickjs` は同じ `rquickjs` major/minor を要求する版を選び、異なる版の `rquickjs` が依存グラフに二重に入った状態を許容しない。実装開始時点の候補は `llrt_buffer 0.8.1-beta` と `rquickjs 0.11` である。採用後は `cargo tree -d` で確認する。

### 7.2 単一バイナリの意味

`cargo build --release` の成果物1ファイルだけで実行できることを意味する。OS の標準 C runtime まで静的リンクすることは初期要件に含めない。まず Linux x86_64 上で受け入れ試験を通し、README にはソースビルド手順と検証済みターゲットを書く。未検証 OS の release packaging は追加しない。

## 8. 処理フロー

```text
CLI parse
  -> function.js 読み込み
  -> compatibility checker
  -> (check はここで終了)
  -> event.json / kvs.json 読み込み・検証
  -> QuickJS runtime を1回分生成
  -> 制限環境と組み込みモジュールを登録
  -> function.js を module として評価
  -> handler(event) を1回呼ぶ
  -> Promise なら完了まで job queue を処理
  -> 戻り値を JSON 化
  -> CloudFront 戻り値モデルを検証
  -> run: JSON 出力 / test: expected と比較
```

各 `run` / `test` プロセスで Runtime と Context を新規作成し、呼び出し後に破棄する。複数実行を使い回すキャッシュは実装しない。

## 9. 静的互換性チェッカー

### 9.1 基本方針

QuickJS は CloudFront runtime 2.0 より広い ECMAScript を受理する。そのため「QuickJS で parse できる」は互換性の証明にならない。SWC で source text を module として parse し、AWS 公式ページの allowlist を `src/checker/runtime20.rs` に型付き定数として転記して AST を検査する。

同じ allowlist を診断テストと runtime のグローバル削除テストから参照し、仕様一覧を複製しない。`docs/compatibility.md` はこの定数から自動生成せず、人が読める要約と差異だけを書く。

### 9.2 必須ルール

診断形式は次で固定する。

```text
<path>:<line>:<column>: error[CFFxxx]: <message>
  help: <修正案またはAWS仕様の短い説明>
```

実装するルール:

| ID | 検査 |
|---|---|
| CFF001 | JavaScript 構文エラー。SWC の recovered error もエラーにする |
| CFF002 | AWS runtime 2.0 の core features 一覧にない AST 構文 |
| CFF003 | `eval()`、間接 eval、`Function` コンストラクタ |
| CFF004 | 未対応の未束縛グローバル。例: `process`, `fetch`, `XMLHttpRequest`, `WebSocket`, `Deno` |
| CFF005 | `setTimeout`, `setImmediate`, `clearTimeout` 等のタイマー |
| CFF006 | 既知の組み込みオブジェクトに対する未対応 static/prototype member の直接参照 |
| CFF007 | `console.log` 以外の console member、または `console.log` の引数が1個以外 |
| CFF008 | `crypto`, `querystring`, `cloudfront` 以外の import/require。相対・絶対ファイル import も拒否 |
| CFF009 | トップレベル `handler` がない、複数ある、または引数が1個でない |
| CFF010 | UTF-8 byte 長が 10 KiB（10 * 1024 bytes）を超える関数コード |
| CFF011 | runtime 2.0 の制約に反する async 構文（async generator、async arrow/closure、async method、async 関数内以外の await） |
| CFF012 | 未対応の `cloudfront` member。初期版では `kvs` 以外を拒否 |

AWS の runtime 2.0 features ページに列挙される Object、String、Number、Math、RegExp、JSON、Array、TypedArray、ArrayBuffer、Promise、DataView、Symbol、TextEncoder、TextDecoder、Date、Function の全 member を `runtime20.rs` へ転記する。省略して「QuickJS にあるから対応」としない。

AST だけで確実に判断できないコードには推測でエラーを出さない。たとえば `obj[name]()`、組み込み関数を引数経由で受け取る場合、ユーザーオブジェクトの `fetch` プロパティは許可する。一方、`globalThis['fetch']` の文字列 literal のように静的に解決できるものは検査する。この限界を `docs/compatibility.md` に明記し、実行時制限で補完する。

### 9.3 診断収集

- 1回の走査で可能な限り全診断を集める。
- `(byte_start, rule_id, message)` で安定ソートし、同じ診断を重複表示しない。
- line/column は1始まり、column は Unicode scalar ではなく表示上の文字位置として扱う。
- parse 不能で AST が得られない場合は CFF001 のみを出して後続走査をしない。
- warning level は初期版では作らない。互換性を断定できないものは docs に限界として記録する。

## 10. CloudFront event / response model

### 10.1 Rust モデル

`serde` の構造体で以下を表現し、CloudFront が拡張した場合に入力を不必要に拒否しないよう、オブジェクトの未知フィールドは保持または無視する。ただし必須フィールドと型は検証する。

- Event: `version`, `context`, `viewer`, `request`, optional `response`
- Context: `eventType` 必須。`distributionDomainName`, `distributionId`, `requestId` は fixture では省略可
- Viewer: `ip`
- Request: `method`, `uri`, `querystring`, `headers`, `cookies`
- Response: `statusCode`, optional `statusDescription`, `headers`, `cookies`, optional `body`
- Value entry: `value`, optional `multiValue`
- Cookie entry: `value`, optional `attributes`, optional `multiValue`

JSON を JavaScript へ渡すときは、一度 Rust モデルへ変換して再構築せず、検証済みの `serde_json::Value` 全体を渡す。これにより未知フィールドを失わない。

### 10.2 入力検証

- `version == "1.0"`。
- `context.eventType` は `viewer-request` または `viewer-response`。
- `viewer-request` では `request` が必須で `response` は不要。
- `viewer-response` では `request` と `response` が必須。
- request body は CloudFront Functions から参照できないため、入力 `request.body` があれば拒否する。
- `request.method` と `request.uri` は文字列。URI は `/` で始まる。
- `headers` のキーは ASCII lowercase。追加・変更後の戻り値にも同じ検査をする。
- `headers`, `cookies`, object 形式の `querystring` は存在しない場合をエラーにせず空 object として扱わない。AWS 形式どおり fixture 側で明記させ、欠落を入力エラーにする。
- `multiValue` がある場合は空配列を拒否し、各要素に `value` が必要。

### 10.3 戻り値検証

- 戻り値は JSON object でなければならない。`undefined`、関数、循環参照、BigInt、NaN/Infinity を含み JSON 化できない場合は実行エラー。
- viewer request では request object または生成 response object を許可する。
- viewer response では response object だけを許可する。
- request を返した場合、入力の `method` が変更されていれば拒否する。
- request の `uri` は `/` で始まる必要がある。
- response の `statusCode` は整数の 100..=599。
- body は文字列、または `{encoding: "text"|"base64", data: string}`。`base64` は実際に decode できることを確認する。
- headers/cookies/querystring の value/multiValue 構造を入力と同じ規則で検証する。

CloudFront がリクエストを HTTP へ戻す際のヘッダー title-case 化、`multiValue` の優先規則、cookie の wire format 化まではシミュレートしない。handler の戻り JSON をそのまま比較対象にする。

## 11. QuickJS runtime

### 11.1 ライフサイクルと安全制限

`RuntimeRunner::execute(source, event, options) -> Result<serde_json::Value>` を公開境界にする。内部では次の順番を崩さない。

1. `rquickjs::Runtime` と `Context` を生成。
2. QuickJS の memory limit を 64 MiB、max stack を 512 KiB に設定。
3. monotonic clock を使う interrupt handler を設定し、JavaScript 実行が1秒を超えたら中断。
4. Buffer と Rust host functions を登録。
5. `bootstrap.js` と `querystring.js` を `include_str!` した文字列から評価。
6. 組み込み module loader を登録。
7. event を JSON 値として context に注入。
8. user source を module として評価し、handler を取得。
9. handler を1回だけ呼び、Promise なら pending job を処理して settle させる。
10. JavaScript 側の `JSON.stringify` 相当で戻り値を JSON 化し Rust 側で parse。
11. Context と Runtime を破棄。

64 MiB/1秒は CLI の安全弁であり AWS の 2 MiB や compute utilization の再現値ではない。エラーメッセージにも `local safety limit` と表示する。

### 11.2 user source のロード

CloudFront のサンプルは `import ...` と export されていないトップレベル `handler` を併用する。実行時には静的検査済みソース末尾へ内部的に `export { handler as __cff_handler };` を追加し、ES module として評価して namespace から呼ぶ。元ファイルは変更しない。

module resolver は `crypto`、`querystring`、`cloudfront` だけを名前解決する。ディスクやネットワークを読む fallback loader は登録しない。CommonJS 互換の `require(name)` も同じ3 module だけを返し、それ以外は即座に例外にする。

### 11.3 制限された global environment

`bootstrap.js` は host API 登録後、user source 評価前に以下を行う。

- `eval` と `Function` は呼び出すと `TypeError` を投げる関数へ置換する。削除だけでなく alias/間接呼び出しも失敗させる。
- timers、`process`、`fetch`、XHR、WebSocket、filesystem/network module は定義しない。
- QuickJS が持つが CloudFront allowlist にない global（例: `BigInt`, `Proxy`, `WeakMap`, `WeakSet`, `Map`, `Set`, `WebAssembly`, `Atomics`, `SharedArrayBuffer`）を global object から削除する。
- allowlist にない既知 built-in prototype/static member は、configurable なら削除する。削除できない QuickJS property は `docs/compatibility.md` に記録し、静的検査を必須の防御にする。
- `console` は `log(value)` だけを公開し、Rust callback 経由で stderr へ出す。複数引数は runtime でも TypeError。
- user code の評価直前に制限対象 object を freeze し、shim の差し替えを防ぐ。ただし user event は通常の可変 object のままにする。

これはセキュリティ sandbox の保証ではなく、CloudFront 互換性テスト用の capability 制限である。信頼できないコードを安全に実行できるとは README に書かない。

## 12. Date の再現

native `Date` を内部変数へ保存し、公開する `Date` を wrapper に置き換える。

- `Date.now()` は invocation start milliseconds を常に返す。
- `new Date()` は invocation start の Date instance を返す。
- 関数としての `Date()` は invocation start の日時文字列を返す。
- `new Date(value)` と複数引数 constructor は native Date へ委譲する。
- `Date.parse`、`Date.UTC`、`Date.prototype` は native の ES5.1 動作を維持する。
- `instanceof Date`、`Object.prototype.toString.call(date)` が通常の Date と同じになるよう prototype を共有する。
- `--now-ms` がない場合は JavaScript 評価開始直前に `SystemTime` を1回だけ読む。途中で読み直さない。

テストでは `Date.now()` をループ中に複数回読むケース、`new Date().getTime()`、`Date()`、明示日時 constructor、別プロセス実行時の再初期化を確認する。

## 13. Buffer

runtime 2.0 では `Buffer` は global として使えるため、user code から import なしで利用可能にする。内部は `llrt_buffer` を使い、AWS 公式 runtime 2.0 ページに列挙された static method、prototype method、`buffer[index]`、`buffer`、`byteOffset`、`length` だけを公開する。

最低限、次の群を公式一覧との対応テストで網羅する。

- 生成: `alloc`, `allocUnsafe`, `from` の string/array/ArrayBuffer/Buffer overload
- 情報・結合: `byteLength`, `compare`, `concat`
- encoding: `utf8`, `hex`, `base64`, `base64url`
- 読み書き: signed/unsigned integer、float、double の BE/LE methods
- instance: `compare`, `equals`, `fill`, `includes`, `indexOf`, `lastIndexOf`, `slice`, `subarray`, `toString`, `write`

LLRT が持つが AWS 一覧にない method は wrapper/prototype pruning で隠す。`allocUnsafe` はローカルで以前のメモリ内容を漏らさずゼロ初期化してよい。この差異は安全性を優先する既知差異として文書化する。

## 14. crypto module

ES module の default export と `require('crypto')` の双方から同じ object を返す。公開 API は次だけとする。

```text
createHash('md5' | 'sha1' | 'sha256')
  .update(string | Buffer | Uint8Array) -> self
  .digest(undefined | 'hex' | 'base64' | 'base64url') -> Buffer|string

createHmac('md5' | 'sha1' | 'sha256', string | Buffer | Uint8Array)
  .update(string | Buffer | Uint8Array) -> self
  .digest(undefined | 'hex' | 'base64' | 'base64url') -> Buffer|string
```

- string は UTF-8 bytes とする。
- `update` は chain 可能で、複数回の内容を順に連結する。
- encoding 省略時は runtime 2.0 どおり Buffer を返す。
- `digest` 後の update/digest、未知 algorithm/encoding、未対応型は TypeError。
- `crypto.subtle`、暗号化、乱数、署名などは公開しない。

RFC の既知ベクトルを使い、各 algorithm の空入力・ASCII・UTF-8・複数 update、各 encoding、HMAC をテストする。期待値を同じ実装で生成してテストしてはならない。

## 15. querystring module

小規模な JavaScript shim として実装し、`bootstrap.js` とは別ファイルにする。AWS 公式一覧どおり以下を公開する。

- `escape(string)`
- `unescape(string)`
- `parse(string, separator='&', equal='=', options)` と alias `decode`
- `stringify(object, separator='&', equal='=', options)` と alias `encode`
- `parse` の `options.decodeURIComponent`, `options.maxKeys`（default 1000、0 は無制限）
- `stringify` の `options.encodeURIComponent`
- 重複 key は最初を string、2個目から array にする。
- 不正 UTF-8 percent sequence は U+FFFD に置換する。

Node.js の querystring 全 API を持ち込まず、この範囲だけを実装する。区切り文字の変更、空値、重複 key、`+`、Unicode、不正 percent、maxKeys を fixture test に含める。

## 16. cloudfront module とローカル KVS

### 16.1 fixture 形式

`--kvs` の JSON schema を次で固定する。

```json
{
  "values": {
    "plain": { "format": "string", "value": "hello" },
    "settings": { "format": "json", "value": { "enabled": true } },
    "binary": { "format": "bytes", "value": "AQID" }
  },
  "meta": {
    "creationDateTime": "2024-01-01T00:00:00.000Z",
    "lastUpdatedDateTime": "2024-01-02T00:00:00.000Z",
    "keyCount": 3
  }
}
```

- bytes の `value` は standard base64。
- `meta.keyCount` は `values` の件数と一致必須。
- fixture がない状態で `cf.kvs()` を呼ぶと「KVS is not associated」の実行時エラー。
- fixture は起動時に全検証し、user code 実行後は変更できない。

### 16.2 JavaScript API

`import cf from 'cloudfront'` の default export へ `kvs()` のみを公開する。`kvs()` は同じ読み取り専用 handle を返す。

- `await handle.exists(key)` は key の存在 Boolean。
- `await handle.get(key, {format})` は Promise。format 省略時は `string`。`string/json/bytes` を許可する。
- 保存 format と要求 format が異なる場合は、string→json は JSON parse、string→bytes は UTF-8 bytes とする。json→string は compact JSON、bytes→string は UTF-8 decode とする。変換不能なら reject。
- `bytes` は Buffer を返す。
- key 不在の `get` は reject、`exists` は false。
- `await handle.meta()` は fixture の meta object の copy。
- `cf.cwt` や未知 member は undefined とし、checker は直接参照を CFF012 にする。

Promise は QuickJS の job queue だけで同期的に settle させ、thread、tokio、実ネットワークを使わない。

## 17. JSON assertion

`serde_json::Value` 同士を再帰比較する。

- object の key 順序は無視する。
- array の順序は比較する。
- string、Boolean、null は完全一致。
- number は JSON number の数値として比較し、`1` と `1.0` は同値とする。両方を有限 `f64` に落として比較するのではなく、整数同士は正確に、整数と小数は正確に同値と判断できる場合だけ同値にする。
- 欠落 key と `null` は別物。
- 最初の差異だけで止めず、最大20件を JSON Pointer の辞書順で表示し、それ以上は残件数を表示する。
- JSON Pointer の `~` と `/` は RFC 6901 どおり escape する。

差分例:

```text
FAIL: JSON values differ (2 differences)
  /headers/cache-control/value
    expected: "max-age=60"
      actual: "max-age=30"
  /statusCode
    expected: 200
      actual: 302
```

object/array 全体を巨大に出さず、差異位置の値だけを compact JSON で出す。値が200文字を超える場合は切り詰めを明示する。

## 18. エラー処理

`AppError` を次の分類にする。

- `Usage`（通常は clap が処理）
- `Io { path, source }`
- `Json { path, line, column, source }`
- `Compatibility(Vec<Diagnostic>)`
- `EventValidation(Vec<ValidationError>)`
- `RuntimeInit`
- `JavaScript { phase, name, message, stack }`
- `LocalLimit { kind }`
- `ReturnValidation(Vec<ValidationError>)`
- `Assertion(Vec<Difference>)`

JavaScript の stack に bootstrap/internal wrapper の frame があれば利用者向け表示では除外し、元 function file の行番号へ補正する。AWS と同一の文言には寄せず、phase（module evaluation / handler invocation / promise settlement / serialization）が分かる安定した文面にする。

## 20. テスト方針

### 20.1 単体テスト

- checker rule、event validation、JSON diff、KVS conversion、crypto vector を純粋関数単位で検証。
- property-based testing は初期版では導入しない。境界値を明示 fixture で固定する。
- snapshot を使う場合は CLI/診断の安定文面だけに限定し、巨大 JSON 全体を snapshot にしない。

### 20.2 統合テスト

- 実バイナリを起動し、stdout/stderr/exit code を別々に検証。
- fixture 名は `valid_*`, `invalid_*`, `unsupported_*` と原因が分かる名前にする。
- 一時刻に依存するテストは必ず `--now-ms` を指定。
- timeout test だけは余裕を持つ上限で判定し、厳密な実行ミリ秒を assertion しない。

### 20.3 互換性 fixture

AWS 公式ドキュメントのコードを引用制限に配慮して最小化・出典コメント付きで fixture 化する。次を最低限含める。

- URI rewrite viewer request
- redirect response
- header/cookie/querystring の変更
- fixed Date
- Buffer base64url
- SHA-256 / HMAC-SHA256
- querystring duplicate key
- async KVS lookup
- eval/timer/process/network rejection

## 21. 受け入れシナリオ

実装完了時に手動または統合テストで次を確認する。

1. `cff-test check valid.js` は code 0、OK 1行。
2. `cff-test check uses_fetch.js` は code 1、CFF004 と正確な行・列。
3. `cff-test run rewrite.js -i request.json` は code 0、変更後 request JSON だけを stdout に出す。
4. 同じ関数内で3回読んだ `Date.now()` は `--now-ms` とすべて一致。
5. `cff-test test rewrite.js -i request.json -o expected.json` は key 順が違っても code 0。
6. 値が違う expected では code 1、JSON Pointer 差分が stderr。
7. crypto の `digest()` encoding 省略は Buffer となり、その Buffer を次の API に渡せる。
8. KVS JSON value と bytes value を async handler が取得できる。
9. KVS 未指定で `cf.kvs()` を呼ぶと code 1 だが panic しない。
10. infinite loop、過大 allocation、循環戻り値のいずれもプロセスを異常終了させず分類済みエラーになる。
11. `cff-test function.js -i event.json -o expected.json` は明示的な `test` と stdout/stderr/exit code が同じ。
12. release binary だけを別ディレクトリへ置いても成功する。

## 24. 実装上の注意

- 要件と無関係なリファクタリングをしない。各 Phase の対象ファイルだけを変更する。
- AWS 仕様に見つからない挙動を Node.js 互換として推測実装しない。
- allowlist と runtime pruning の差異を見つけたら、まず再現テストを追加してから修正する。
- QuickJS/LLRT のエラー文をそのまま golden test にせず、`cff-test` が所有する prefix・分類・位置だけを安定契約にする。
- embedded JavaScript は Rust 文字列へ直書きせず `.js` ファイルを `include_str!` する。単一バイナリ要件は維持される。
- source、event、expected、KVS を読み込む権限は CLI 自身に必要だが、そのパスや内容を JavaScript global へ公開しない。
- 実装中に AWS 仕様とこの文書が矛盾した場合は、勝手に仕様を選ばず、矛盾・影響範囲・推奨変更を記録して依頼者へ確認する。
